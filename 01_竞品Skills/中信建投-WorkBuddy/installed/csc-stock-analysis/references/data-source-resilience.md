# 数据源环境层观测（随实现变化即作废）

> ⚠️ **本文件是环境观测层，不是架构流程**。以下内容（错误码、超时秒数、退避秒数、重试次数）来自对翼答 MCP 的**实测快照**，**随数据源实现变化即作废**。
> - 主流程（SKILL.md / error-handling.md）**只认架构约束**：串行天然间隔、失败重试 1 次、限流才退避、单维连败即降级。
> - 本文件的任何数字**不得**写进主流程作为强制步骤；需要调参时只改这里。
> - 换数据源时本文件整体重写或删除。

## 一、实测错误码与应对（翼答，2026-09 实测）

| 现象 | 实测特征 | 架构层应对 | 环境层建议（可调） |
| --- | --- | --- | --- |
| `errcode 30004` 服务异常（秒拒） | 约 3s 即返回空，无数据 | 视为一次失败 → 重试 1 次 | 命中限流特征时静默短退避后重发原句；**退避秒数由环境层定** |
| `504` 网关挂起 / 过载 | 请求在网关挂满约 62s 才回 504，返回 0 字节 | **早放弃**：客户端超时设小值，不等满 62s；放弃后收窄问题粒度重发 | 客户端超时建议 20s（不要白等 62s）；超时即视为该次失败，走重试/降级 |
| `429` 频率超限 | `您的使用量已超出频率限制，将在 XX:XX:XX UTC+8 重置` | 属用户侧额度问题，**不傻等**；直接降级该维度并标注"接口限流" | 不盲目退避赌重置；可提示用户错峰 |
| 标准 MCP 通道瞬时回收 | 偶发 `Connection closed` | 瞬时错误 → 重试 1 次即可，不要当成持久故障去绕路（如改 HTTP 直连） | — |
| `Connection closed` / `30004` **连续多轮交替出现** | 单股全流程跑到第 6~8 条后开始高频出现，原句重发常继续失败 | 仍按"重试 1 次即降级"，**不要把失败重试写进主流程** | 实测**更换 `session_id` 后立即恢复**（同一 question 有效）；可把"重试时换 session_id"作为环境层手段，秒数与换 id 策略均只在本文件调 |
| **全类别 `status_code: -3001` / `no answer availabe!`** | HTTP 200 + 正常 JSON 信封，但 `answer: []`、`status_code: -3001`；**任何问法、任何标的、换 `session_id` 均复现**（含 SKILL.md 的标准探测问句） | **先查 `source` 入参取值是否为本文件/配置文件的当前值**（实测根因就是 `source` 传了错值）；取值正确后仍复现，才判数据源整体不可用，按 `error-handling.md` §2 降级，**禁止**用 web_search / 训练数据兜底 | 2026-09-21 实测：`source=b_zhengquan_zx`（错）→ 全量 `-3001`；改为 `source=b_zhengquan_zxjt`（对）→ 立即返回正常结果。属**入参取值问题，不是故障**；当日曾误判为后端宕机，勿重蹈。`-3001` 本身不是 401/403/429，不触发 API Key 门控 |
| 返回体被截断并落盘（>约 90KB） | 工具把 SSE 全文写入临时 txt，对话里只剩提示 | 读该文件解析，**不要**当成数据缺失；单次调用体积本身不构成降级理由 | — |
| **长/复杂问法秒拒或挂死** | 含"最近N个交易日日K线"（N≥120）、"公告+编号+正文限制"等多要素长句时，高概率 `errcode 30004`（约 4s 秒拒）或 `504`（挂约 61s） | 换**简化单主题问法**重问（如「{名称}{代码}最近三个月的公告标题」→ 命中"查公告"、`{名称}{代码}股权质押` → 命中"事件查询"） | 2026-09-21 实测：新闻/公告/事件四个字以下的主语+单主题问法成功率明显更高；同一问法隔轮重试也可成功 |
| **`502 Bad Gateway` 间歇出现** | 网关秒回 502，持续数十秒到数分钟 | 视为该次失败 → 按"重试 1 次"处理，**不要**改用 web_search | 本次实测 502 与 30004 交替出现，属网关侧波动 |
| **相对窗口「最近 N 个交易日」仍约 30 行** | 问"最近60个交易日"也只返回约 1 个月（30 行）。2026-09-24 复测该窗口不再 504，行数上限还在 | 长序列改走显式日期的日 K 线（开高低收+成交量），见 `data-source-queries.md` §1.3。短序列不够时，MA60/120/250 走批4b | 2026-09-21 起多次实测。显式日期可到约 243 行；加大「最近 N 日」的 N 不会变长 |

## 一·B、数据内容缺陷（接口正常返回，但字段值不可用）

> 这类问题**不是**接口故障，重试无用；主流程按"字段不可用 → 显式降级"处理，不得静默使用。

| 字段 | 实测现象 | 应对 |
| --- | --- | --- |
| 券商类标的的「销售净利率」 | 返回 **342%~354%**，明显口径异常（>100% 不可能） | 券商/金融类标的一律**不使用**该字段作判断，报告中标注"口径异常" |
| 「涨跌幅:前复权」（资金流表内） | 与收盘价序列自算值存在 **≈0.1pp** 偏差（实测 0.37% vs 0.27%） | 涨跌幅一律以**收盘价序列自算**为准（`(今收/昨收−1)×100`），差异在报告中标注 |
| 「主力资金流向」「dde大单净额」最新一日 | 值以**科学计数法字符串**返回（如 `"-6.36E7"`） | 解析时统一 `float()` 转换，勿按数值直接参与运算 |
| 批5①「最近30个交易日的主力资金流向」 | 2026-09-30 实测**只回 7 行**（近 7 个交易日），不足以本地算 10 日聚合 | 按 §5.2 单问「最新的主力资金净额、超大单净额、5日主力净额、10日主力净额、主力资金连续流入天数」补取；该问实测返回 30 行主力资金流向 + 30 行特大单净额，可同时补齐序列与聚合 |
| §5.2 rich_text 给出的 5 日主力净额 | 2026-09-30 实测 rich_text 为 **-59.54 亿元**，而同一批 30 行逐日序列本地汇总为 **-60.79 亿元**（差 ≈1.25 亿元）；10 日值两者一致（-61.94 亿元） | 聚合值一律以**逐日序列本地汇总**为准，rich_text 的聚合数字仅作交叉校验 |
| 批5 返回的列 | 「资金比」列在批5①与 §5.2 中均未返回 | 报告模板的资金比列写「未获取到数据（数据源本次未返回该字段）」，不得省列 |
| 批7 合并问的行业指数 | 2026-09-30 实测：申万一级行业分类（rich_text）✓、三大指数收盘价/涨跌幅 ✓、成分股口径涨跌家数 ✓，但**行业指数逐日序列未以可解析值返回**（`rich_text` 仅留 `visual` 占位） | 按 §6.2 单问「{行业}指数最近10个交易日的收盘点位和涨跌幅」补取；该单问实测仍以 `rich_text` 文本片段给出个别交易日点位与涨跌幅，需从文本提取，缺日则写窗口不全 |
| 「支撑位」字段与现价的相对位置 | 2026-09-30 实测中际旭创**支撑位 858.00 元高于现价 808.44 元**（此前标注的支撑位已被跌破，字段仍返回原值） | 如实呈现"现价低于支撑位 X%"，**不得为满足支撑位<现价<压力位的排序而改写数值或改口径** |
| 概念/事件类表的 `columns[].label` | `label` 可能被替换为无意义串（如两个列同时叫「风险等级B」），真实列名在 `key` / `index_name` / `feKey` | **按 `key` 取列名**，行数据键即该 `key`；只按 `label` 过滤会误判为"无结构化数据" |
| 非银金融（保险）行业指数 | 2026-09-30 实测 601318：批7 合并问与 §6.2 单问**均未**返回可解析的行业指数逐日序列；改用显式代码（801790.SL / 801790.SI / 861096.TI）单问亦全部返回"暂无" | 行业校准如实记为"未获取到数据（行业指数接口暂不可得）"。**不得**据个股涨跌幅反推行业强弱，更**不得**用中证全指保险指数（H30186）的历史点位冒充实时值 |

## 二、超时与退避参数（快照，非强制）

| 参数 | 2026-09 实测建议值 | 说明 |
| --- | --- | --- |
| 单次调用客户端超时 | 默认 40s（`SKILLHUB_HTTP_TIMEOUT` 可覆盖） | 防 504 白等 62s。**取值只落在 `mcp_skillhub_call.py` 的 `DEFAULT_TIMEOUT`**（环境变量名 + 默认值），主流程不感知 |
| 失败重试次数 | 主流程 1 次；环境层可放宽至 3~5 次 | 用户决策：主流程失败只重试一次即可；网关高频抖动期由环境层放宽 |
| 重试前退避 | 仅短退避（1~3s） | 非限流失败不插固定 sleep（串行已天然间隔） |
| 单维度连败降级阈值 | 主流程：重试 1 次仍失败即降级 | 不等 3 次；降速靠减少调用次数而非加间隔 |
| 受控并发窗口 | 串行（1 路） | 并发上限是数据源属性，声明在 `data-source-config.md`；主流程恒为串行单发，不因本行改变 |

## 三、为什么这些数字不能固化进主流程

- 翼答后端会扩容/限流策略会变，今天 504 多、明天可能 20s 全通；
- 把"等 30~62s 再试"写死，等于把环境波动转嫁成用户固定等待；
- 正确做法是**架构层只约束"重试 1 次 + 限流才退避 + 失败即降级"**，具体秒数外置到此文件，随测随改。

## 四、2026-10-16 追加实测（快照，随实现变化即作废）

> 本轮场景：双股技术面专项对比（中际旭创 300308 × 新易盛 300502），约 27 次成功取数。以下为本轮新观察到、**与前文不重复**的现象。

| 现象 | 实测特征 | 架构层应对 | 环境层建议（可调） |
